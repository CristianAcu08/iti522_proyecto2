# Tabla de Cambios respecto al Proyecto 1

| Elemento | Decisión (Proyecto 1) | Decisión (Proyecto 2) | Justificación Técnica |
|----------|-----------------------|-----------------------|------------------------|
| Motor de Base de Datos | Servicio gestionado (Azure PostgreSQL Flexible Server o AWS RDS) | Motor auto-administrado en VM (PostgreSQL 15) | Restricción legal del departamento legal: el contrato de licenciamiento solo es válido si la empresa mantiene el control administrativo del motor. Un servicio gestionado requeriría re-licenciamiento no aprobado. |
| Servicio de Aplicación | Azure App Service (o equivalente) | Azure App Service (mantener) | No hay restricción que lo prohíba. Ofrece buen balance de control y facilidad de despliegue para la capa web. |
| Almacenamiento de Archivos Estáticos | Azure Blob Storage (o CDN) | Azure Blob Storage (mantener) | Ideal para servir imágenes de productos y backups lógicos. Bajo costo y alta durabilidad. |
| Arquitectura de Alta Disponibilidad | Dependía de características gestionadas (zonas de disponibilidad, escalado automático avanzado) | Se mantiene App Service con escalado básico, se añaden NSG y estrategias de backup/restore | Dado que no podemos usar BD gestionada, nos enfocamos en: (1) backup automatizado y restauración demostrada, (2) monitoreo básico, (3) diseño resistente a fallos mediante capacidad de recuperación rápida. |
| Acceso desde Dispositivos Móviles | Se proponía diseño responsivo o PWA | Se mantiene diseño responsivo | Requisito explícito: accesible desde teléfono. El diseño responsivo cumple sin necesidad de complejidad adicional de PWA o nativa. |
| Modelo de Responsabilidad (Shared Responsibility) | Proveedor gestiona infra, plataforma y parcialmente la aplicación | Grupo gestiona todo lo relacionado con la BD (VM, SO, motor, datos) y colabora en el despliegue y operación de la web | Cambio derivado de la restricción: el grupo asume más tareas operativas (parcheo, backup, tuning) que en un modelo gestionado serían responsabilidad del proveedor. |
| Herramientas de IaC (Infraestructura como Código) | Se proponía usar ARM/Terraform (opcional) | Se mantiene el uso de scripts básicos y documentación manual (por simplicidad y tiempo) | Aunque ideal usar IaC, el enfoque está en demostrar operabilidad y conocimiento. Los scripts de instalación y backup servirán como evidencia de comprensión. |
